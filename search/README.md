# Поисковая система: токенизация, булев индекс, стемминг и анализ частот

Поисковый движок и HTTP-сервис написаны на C++20 с userver. Сервер загружает
индекс BIDX при старте и обслуживает API и небольшой интерфейс на HTML/JavaScript.
В форме «Индекс BIDX» можно выбрать файл и загрузить его для текущего запуска сервиса.
После успешной проверки поиск, статистика и замеры поиска используют загруженный индекс.
Замеры токенизации выполняются по отдельно настроенному исходному корпусу.
Поиск по умолчанию учитывает русские словоформы; точный режим сохраняется.
Раздел «Ципф» показывает частоты активного индекса, а «Качество поиска» сравнивает режимы по разметке.
В алгоритмах индексации и поиска используются строки и массивы. Подготовка
корпуса ЛР1 выполняется отдельно.

## Модули и классы

Библиотеки индекса и поиска имеют собственные заголовки и исходники:

```text
search/
├── index/
│   ├── include/             # индекс, токенизатор, читатель корпуса и замер токенизации
│   ├── src/                 # реализация и CLI индексатора
│   └── CMakeLists.txt
├── boolean_search/
│   ├── include/boolean_search/
│   ├── src/                 # BooleanSearch и парсер запросов
│   └── CMakeLists.txt
├── morphology/              # include/src: RussianStemmer, собственные правила Snowball Russian
├── analysis/                # include/src: ZipfAnalysis и SearchQualityBenchmark
├── common/                  # общий класс собственной сортировки слиянием
├── service/
│   ├── src/                 # компоненты userver и HTTP-обработчики
│   ├── frontend/            # поиск, статистика и замеры
│   └── static_config.yaml
├── tests/                   # проверки модулей и их взаимодействия
└── CMakeLists.txt            # подключение модулей и тестов
```

Индекс и булев поиск — отдельные библиотеки с разными пространствами имён.
`search_index` (namespace `indexing`) работает с корпусом и двоичным индексом;
`boolean_search_core` (namespace `boolsearch`) использует готовый `Index`.
Индексатор связывается только с `search_index`: булев парсер ему не нужен.

| Класс | Заголовок | Назначение |
|---|---|---|
| `indexing::Tokenizer` | `index/include/tokenizer.hpp` | Методы `Tokenize()` и `Utf8Length()`: UTF-8, выделение слов, понижение регистра. |
| `indexing::CorpusReader` | `index/include/corpus_reader.hpp` | Метод `Next()`: чтение и декодирование одного документа TSV для индексатора и замера. |
| `indexing::TokenizationBenchmark` | `index/include/tokenization_benchmark.hpp` | Метод `Run()`: прогрев, повторные замеры префиксов и статистика токенизации. |
| `indexing::Indexer` | `index/include/indexer.hpp` | Метод `Build()`: чтение TSV, использование `Tokenizer`, сортировка и построение индекса в памяти. |
| `indexing::IndexSaver` | `index/include/index_saver.hpp` | Метод `Save()`: сериализация BIDX и запись через `std::ofstream` в бинарном режиме. |
| `indexing::IndexLoader` | `index/include/index_loader.hpp` | Метод `Load()`: чтение и проверка BIDX. |
| `indexing::detail::IndexFormat` | `index/include/index_format.hpp` | Структуры двоичных записей с операторами `>>` и `<<`. |
| `indexing::Index` | `index/include/index.hpp` | Данные индекса, методы чтения `documents()`, `terms()`, `statistics()` и двоичный поиск `Lookup()`. |
| `boolsearch::BooleanSearch` | `boolean_search/include/boolean_search/query.hpp` | Метод `Search()`: разбор запроса и операции над списками документов. |
| `morphology::RussianStemmer` | `morphology/include/russian_stemmer.hpp` | Метод `Stem()`: основа русского слова по правилам RV/R2 и суффиксам. |
| `boolsearch::StemIndex` | `boolean_search/include/boolean_search/stem_index.hpp` | Отсортированные основы и объединённые списки; строится один раз. |
| `analysis::ZipfAnalysis` | `analysis/include/zipf_analysis.hpp` | Ранги, модели Ципфа/Мандельброта и выбор точек графика. |
| `analysis::SearchQualityBenchmark` | `analysis/include/search_quality.hpp` | Сравнение exact/stem, P@20, полнота в пуле, время. |

Реализации находятся в `index/src/` и `boolean_search/src/`. Поля `Index`
закрыты, методы доступа возвращают константные ссылки. `BooleanSearch` хранит
ссылку на индекс, поэтому индекс должен существовать дольше объекта поиска.
Сборка и сохранение — разные операции:

```cpp
#include "boolean_search/query.hpp"
#include "index_saver.hpp"
#include "indexer.hpp"

indexing::Indexer indexer;
indexing::IndexSaver saver;
auto index = indexer.Build("corpus.tsv");
saver.Save(index, "index.bin");

boolsearch::BooleanSearch engine(index);
auto documents = engine.Search("руки !ноги");
```

Основные методы показывают порядок этапов, а детали находятся в отдельных методах:

- `Build()`: чтение корпуса, сбор вхождений, сортировка, построение списков документов.
- `Save()`: расчёт смещений, заголовок и каталог секций, документы, термы, списки, статистика.
- `Load()`: чтение файла, проверка заголовка и секций, восстановление данных индекса.

Формат описан структурами `Header`, `Section`, `DocumentRecord`, `TermRecord`,
`PostingRecord`, `StatisticsRecord`, `IndexingRecord` и `FrequencyRecord`. У каждой записи есть операторы `>>` и `<<`
для стандартных потоков. Реализации находятся в `index/src/index_format.cpp`.
`IndexLoader` проверяет границы секций, ссылки между записями, UTF-8 и порядок данных.

В `boolean_search/src/query.cpp` находятся операции над списками документов,
в `query_parser.cpp` — разбор запроса. Компонент `SearchIndex` загружает индекс,
набор запросов для замеров и HTML при запуске. HTTP-обработчики используют
один общий индекс для поиска и измерений.

## Стиль C++

За основу принят [Google C++ Style Guide](https://google.github.io/styleguide/cppguide.html)
с перечисленными ниже соглашениями проекта.
Файл `.clang-format` задаёт отступ в четыре пробела, ограничение строки
в 121 столбец и порядок подключений; для ветвлений и циклов используются
фигурные скобки. Методы называются `PascalCase` (`Build`, `Save`, `Search`),
поля классов — `snake_case_`, константы и элементы перечислений — `kPascalCase`.
Методы доступа, например `documents()`, сохраняют `snake_case`, как разрешено
руководством. Заголовки используют защиту от повторного включения; каждый файл
подключает заголовки используемых типов напрямую. Переменные объявляются
по одной, числовые преобразования используют C++-касты. Интерфейсы классов
явно задают копирование и перемещение; комментарии описывают владение,
время жизни ссылок и возможность параллельного чтения.

Соглашения проекта, отличающиеся от строгого Google Style: четыре пробела, 121 столбец,
расширения `.cpp`/`.hpp`, классы со статическими вспомогательными методами
и ошибки через исключения.
`BooleanSearch` сохраняет ссылку на индекс: передача временного индекса запрещена,
а требование к времени жизни описано в заголовке. Основной сценарий располагается
перед вспомогательными методами. Подготовка данных, обработка и возврат результата
разделяются пустыми строками; комментарии поясняют ограничения и причины решений.
Лицензионные заголовки отсутствуют: лицензия в репозитории не задана.

Форматирование исходников из корня репозитория (clang-format 15 или новее):

```sh
rg --files search/index search/boolean_search search/service search/tests \
  -g '*.cpp' -g '*.hpp' -0 | xargs -0 clang-format -i
```

Для проверки без изменения файлов замените `-i` на `--dry-run --Werror`.

Файл `.clang-tidy` включает доступные проверки Google, прямых подключений,
именования и отдельных объявлений переменных. Проверка всех C++-файлов:

```sh
cmake -S search -B search/build -DCMAKE_EXPORT_COMPILE_COMMANDS=ON
rg --files search/index search/boolean_search search/service search/tests \
  -g '*.cpp' -0 | xargs -0 -n 1 clang-tidy -p search/build
```

Эти проверки дополняются ручным просмотром интерфейсов, времени жизни объектов
и комментариев; автоматическая проверка охватывает только часть руководства.

## Быстрый запуск

Из корня репозитория соберите сервис с демонстрационным индексом. Dockerfile
использует официальный образ userver 3.2 для Linux x86-64.

```sh
docker build --platform linux/amd64 -t websearch-userver search
docker run --rm --platform linux/amd64 \
  -e SEARCH_ADDRESS=0.0.0.0 -p 127.0.0.1:8081:8081 websearch-userver
```

Откройте [интерфейс поиска](http://127.0.0.1:8081).
Для существующего корпуса передайте индекс контейнеру в режиме чтения:

```sh
docker run --rm --platform linux/amd64 \
  -e SEARCH_ADDRESS=0.0.0.0 -e SEARCH_INDEX=/corpus.bin \
  -p 127.0.0.1:8081:8081 \
  --mount "type=bind,source=$PWD/search/data/corpus.bin,target=/corpus.bin,readonly" \
  websearch-userver
```

При локальной сборке укажите установку userver 3.2 или новее через
`CMAKE_PREFIX_PATH`, если она находится вне системных каталогов. Нужны C++20
и заголовки utf8proc. Относительные пути конфигурации отсчитываются от `search/`.

```sh
cmake -S search -B search/build -DCMAKE_BUILD_TYPE=Release \
  -DSEARCH_BUILD_WEB=ON -DUSERVER_FEATURE_TESTSUITE=OFF
cmake --build search/build --parallel
cd search
build/boolean_index data/demo.tsv data/demo.bin
build/search_service -c service/static_config.yaml
```

`SEARCH_ADDRESS`, `SEARCH_PORT` и `SEARCH_INDEX` задают адрес, порт и файл
индекса. По умолчанию используются `127.0.0.1`, `8081` и `data/demo.bin`.
`TOKENIZER_CORPUS` задаёт TSV для замера токенизации, по умолчанию `data/demo.tsv`.
`boolean_index` сохраняет длительности построения и записи и частоты термов в BIDX 1.2.
Статистика показывает число термов, среднюю длину терма, общее время индексации,
мс/документ, мс/КиБ, документов/с и КиБ/с. КиБ равен 1024 байтам заголовков и
статей. Для старого индекса время появляется после повторной индексации.
По умолчанию `SEARCH_BUILD_WEB=AUTO`: при наличии userver CMake добавляет
веб-сервис, иначе собирает индексатор и тесты ядра. Режим `ON` требует
установленный userver, а режим `OFF` всегда собирает только ядро.
Если старый профиль CLion сохранил `SEARCH_BUILD_WEB=ON` в кэше, задайте
`-DSEARCH_BUILD_WEB=AUTO` в настройках профиля CMake и перезагрузите проект.

## Корпус ЛР1

Индексатор принимает UTF-8 TSV **без заголовка**. Каждая непустая физическая строка:

```text
заголовок<TAB>URL<TAB>текст статьи
```

В полях обратная косая черта кодируется как `\\`, табуляция — `\t`, перевод
строки — `\n`, возврат каретки — `\r`. Сам разделитель полей — настоящая табуляция.
BOM в начале файла и CRLF поддерживаются. Пустые строки пропускаются;
непустая строка обязана содержать ровно три поля. Заголовок и URL непустые.
Заголовок и текст индексируются, URL только сохраняется. Идентификаторы
назначаются с нуля в порядке входных документов. Повторные URL не объединяются.
TSV — только входной корпус; поисковый индекс полностью двоичный.

В существующей ЛР1 MongoDB содержит `page_content` с `page_id`, `title`,
`text_content`, а PostgreSQL — `pages.id`, `pages.url`. Вспомогательный Python-
экспортёр связывает эти исходные данные; он не участвует в индексации или поиске.
Он использует уже имеющиеся зависимости проекта `pymongo` и `psycopg2`.

```sh
.venv/bin/python search/tools/export_corpus.py \
  --env .env --host tbm-qa.digital --postgres-port 7432 \
  --output search/data/corpus.tsv
search/build/boolean_index search/data/corpus.tsv search/data/corpus.bin \
  > search/data/index-metrics.json
```

Экспорт выполняет только чтение. Пароли берутся из `.env`, не передаются в
аргументах команд и не включаются в отчёт. Исходный корпус, двоичные индексы,
результаты с заголовками и сборки исключены из Git. При изменении корпуса индекс
нужно построить повторно; работающий сервер перезапустить.

## Запросы и HTTP API

```text
московский авиационный институт
(красный || желтый) автомобиль
руки !ноги
(москва || петербург) && !(спорт || футбол)
```

Приоритет: `!`, затем И (пробел/`&&`), затем `||`. Скобки меняют приоритет.
Смежные операнды, например `автомобиль!(красный||желтый)`, также означают И.
Повторные пробелы, табуляции, Unicode-разделители и знаки пунктуации между
словами допустимы. Пустой запрос возвращает пустую выдачу. Неизвестное слово
не даёт совпадений; `!неизвестноеслово` возвращает весь корпус. НЕ вычисляется
относительно всех документов индекса. Регистр ASCII и русского алфавита
понижается, включая `Ё`. По умолчанию русские словоформы объединяются стеммером
с заменой ё на е. В режиме `mode=exact` **ё и е различаются**, словоформы сохраняются.
Незакрытые скобки, одинокие `&`/`|` и пропущенные операнды дают ошибку.
Ограничения: 65 536 байтов запроса, 4096 лексем, 128 уровней скобок.
Результаты упорядочены по DocId, ранжирования нет.

| Запрос | Результат |
|---|---|
| `GET /` | Интерфейс поиска и статистика индекса. |
| `GET /?view=benchmark` | Форма запуска замеров и таблица результатов. |
| `GET /?view=analysis` | Логарифмический график частот с моделями Ципфа и Мандельброта. |
| `GET /api/search?q=…&page=1` | До 50 результатов, общее число совпадений, номер и количество страниц, время поиска. |
| `GET /api/stats` | Число документов, термов и токенов, размеры, средние длины, время загрузки. |
| `POST /api/index/load?filename=…` | Загрузка BIDX в теле `application/octet-stream`; ответ содержит имя и статистику активного индекса. |
| `GET /api/benchmark` | Запросы и параметры замера по умолчанию. |
| `POST /api/benchmark` | Прогрев и замеры для переданных запросов. |
| `GET /api/benchmark/tokenizer` | Имя корпуса, три повторения по умолчанию, максимум 10. |
| `POST /api/benchmark/tokenizer` | Прогрев и замеры токенизации префиксов 1%, 10%, 100% документов. |
| `GET /api/analysis/zipf` | Параметры, log10 RMSE и до 2 000 точек графика активного индекса. |
| `GET /api/analysis/zipf?format=tsv` | Полная таблица рангов, термов, cf и предсказаний моделей. |
| `GET /api/benchmark/quality` | Доступность разметки для текущего SHA-256 и параметры замера. |
| `POST /api/benchmark/quality` | Сравнение точной формы и стемминга на размеченных запросах. |

Загруженный файл проходит проверки `IndexLoader` во временном файле на отдельном
обработчике. После проверки сервис заменяет активный снимок индекса. Каждый
запрос поиска, статистики и замеров удерживает один снимок до завершения.
Ошибка загрузки сохраняет предыдущий индекс. Временный файл удаляется при
успехе и при ошибке. После перезапуска используется `SEARCH_INDEX`.

Лимит загрузки по умолчанию — 256 МиБ. Он задаётся полем `max_request_size`
для `handler-load-index` в `service/static_config.yaml`. Имя файла служит
подписью в интерфейсе. Одновременно обрабатывается одна загрузка.
Неверный BIDX возвращает HTTP 400, неподходящий тип содержимого — 415,
превышение размера — 413. Поле `index_name` присутствует в ответах поиска,
статистики и выполненного замера.

```sh
curl -H 'Content-Type: application/octet-stream' \
  --data-binary @search/data/corpus.bin \
  'http://127.0.0.1:8081/api/index/load?filename=corpus.bin'
```

## Поиск из командной строки

Утилита загружает индекс один раз и выполняет каждый запрос из stdin.
Каждая строка stdout — самостоятельный JSON-объект с `query`, `total`,
`elapsed_ms`, `results` и `mode`. Список содержит все совпадения в порядке DocId.
Пустая строка запроса даёт пустую выдачу. Поддерживаются LF, CRLF и последняя
строка без перевода строки.

```sh
search/build-clion-userver/boolean_search search/data/corpus.bin \
  < search/data/queries.txt > search/build-clion-userver/results.jsonl
```

Дополнительный аргумент `--mode exact` включает поиск по исходной форме,
`--mode stem` явно выбирает режим по умолчанию. HTTP принимает такой же
параметр `mode=stem|exact`, а POST замера поиска — поле `"mode":"exact"`.
Режим сохраняется в ссылках страниц и истории; размер страницы остаётся 50.

При ошибке отдельного запроса выводится запись с `query` и `error`, затем
чтение продолжается. Для некорректного UTF-8 поле `query` равно `null`.
Код завершения — 0 при успехе, 2 при ошибках запросов, 1 при ошибке загрузки
индекса или ввода-вывода. Операционные сообщения идут в stderr.

Поиск возвращает `results` с полями `id`, `title` и `url`. Запрос и номер
страницы сохраняются в URL интерфейса. Некорректный запрос или номер страницы
возвращает HTTP 400 с полем `error`.

## Замеры

Для замера поиска в теле POST `/api/benchmark` передайте JSON, например
`{"queries":["руки !ноги","и"],"repetitions":10}`.
Без `queries` используются строки файла `data/benchmark-queries.txt`. Допускается
до 20 запросов и от 1 до 100 повторений каждого. Перед замером каждый запрос
выполняется один раз для прогрева. Ответ содержит число совпадений, минимум,
среднее и максимум в миллисекундах. Измеряется вычисление результата, отдельно
от загрузки индекса, сериализации и HTTP. Время загрузки доступно в статистике.

На вкладке «Замеры» можно выбрать «Токенизация». Источник задаётся полем
`search-index.tokenizer-corpus-path` в конфигурации или `TOKENIZER_CORPUS`;
выбранный в веб-форме BIDX его не меняет. Имя TSV отображается рядом с результатом.
Запуск на полном подготовленном корпусе из корня репозитория:

```sh
cd search
SEARCH_INDEX=data/corpus.bin TOKENIZER_CORPUS=data/corpus.tsv \
```

```sh
curl -H 'Content-Type: application/json' -d '{"repetitions":3}' \
  http://127.0.0.1:8081/api/benchmark/tokenizer
```

Замер использует префиксы `ceil(D × p / 100)` документов для `p = 1, 10, 100`.
Перед каждым префиксом выполняется один прогрев, по умолчанию затем три
измерения (допустимо 1–10). Ответ содержит фактические документы, байты
декодированного текста, токены, средние длины в кодовых точках и байтах,
массив `runs`, среднее время токенизатора `tokenization_mean_ms` и полного
прохода `total_mean_ms`. Полный проход включает чтение, декодирование,
токенизацию, подсчёт длин и освобождение результата. Сортировка индекса
не выполняется. Подготовительный подсчёт документов и HTTP находятся вне замеров.
`ms_per_kib` и `kib_per_second` рассчитаны по времени токенизатора и объёму
декодированных заголовков и статей; КиБ = 1024 байта. Счётчики повторений
проверяются на совпадение. Неверный корпус или параметры дают JSON-ошибку HTTP 400.

## Частоты и качество поиска

Индексатор создаёт BIDX 1.2 с частотами всех вхождений термов до удаления
повторов. Раздел «Ципф» использует эти cf, а не длины списков документов.
Ципф `C/r` и Мандельброт `C/(r+q)^s` подбираются в C++ по всем рангам.
Веб-график выбирает до 2 000 точек; полная таблица доступна по `format=tsv`.
Старые BIDX 1.0/1.1 продолжают поддерживать оба режима поиска, но для частот
требуется перестроение. Статистика API также содержит `stem_terms`,
`has_frequencies` и `index_sha256`.

Вариант «Качество поиска» сравнивает exact/stem по фиксированной разметке
из `SEARCH_QUALITY_DATASET` или `data/relevance-judgments.json`. Файл содержит
16 запросов, их намерения и 486 оценок top-20 пулов. Это диагностические оценки
ассистента; методика и ограничения указаны в отчёте. Возвращаются число
совпадений, P@20, полнота в размеченном пуле и время каждого режима.
По умолчанию — один прогрев и три измерения, допускается 1–100 повторений.

```sh
curl -H 'Content-Type: application/json' -d '{"repetitions":3}' \
  http://127.0.0.1:8081/api/benchmark/quality
```

Разметка привязана к SHA-256 полного файла `data/corpus.bin`. Для демоиндекса
и других файлов GET возвращает `available:false`, POST — JSON-ошибку HTTP 400.
После нового построения меняется и время в BIDX, поэтому разметку нужно
проверить и связать с новым файлом. Сервис не считает неразмеченные результаты
нерелевантными. Исходный индекс 1.1 сохранён как `data/corpus-v1.1.bin`.

Полные данные и команды построения SVG/PNG находятся в
[отчёте по Ципфу](reports/zipf.md); Matplotlib нужен только для самостоятельной
генерации этих фигур. Сам сервис и основной анализ написаны на C++.

## Проверки и отчёты

Тесты написаны на GoogleTest и автоматически регистрируются в CTest.
Для локальной сборки тестов нужны установленный GoogleTest (`brew install googletest` на macOS)
и Python 3 для проверки экспортёра. Сборку тестов можно отключить флагом `-DBUILD_TESTING=OFF`.
При наличии Node.js CMake добавляет GoogleTest-проверку логики frontend.
Тест стеммера проверяет 49 785 готовых эталонных пар Snowball; исполняемого
кода Snowball в приложении нет.

```sh
ctest --test-dir search/build --output-on-failure
```

Для профиля CLion `macos-userver` каталог сборки — `search/build-clion-userver`.

Сборку в контейнере можно проверить командой:

```sh
docker run --rm --platform linux/amd64 --entrypoint ctest \
  websearch-userver --test-dir /app/build --output-on-failure
```

Тесты проверяют формат BIDX, булеву семантику на независимом эталоне,
пагинацию, статистику, замеры и обработку ошибок. HTTP-тесты запускают
`boolean_index` и `search_service` на тестовом корпусе и отправляют запросы
через временный Unix-сокет. Тесты экспортёра вызывают его Python-функции
в отдельном процессе без подключения к базе.
Тесты CLI передают потоки в `SearchCli::Run`. Тесты хранилища проверяют замену
индекса, сохранение старого снимка у читателя и обработку ошибочных загрузок.
Тесты `CorpusReader` и `TokenizationBenchmark` проверяют TSV, размеры префиксов,
счётчики, средние, формулы и пустой или повреждённый вход. Временных порогов нет.
Планы, обоснование сценариев и приложенные результаты находятся в отчётах.

- [ЛР1 — Токенизация](reports/tokenizer.md) — правила, состав корпуса, нормализация и измеренная скорость.
- [ЛР3 — Булев индекс](reports/indexer.md) — представление, сортировка, замеры и рост корпуса.
- [ЛР4 — Булев поиск](reports/boolean-search.md) — грамматика, скорость запросов и проверка выдачи.
- [Закон Ципфа](reports/zipf.md) — распределение, две модели, константы и полные частоты.
- [Стемминг](reports/stemming.md) — поиск словоформ и оценка улучшений/ухудшений качества.
- [Спецификация BIDX](FORMAT.md) — побайтовое описание формата.
