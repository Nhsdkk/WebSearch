# ЛР3 — Булев индекс

## Вход и представление документов

`boolean_index` читает экспорт ЛР1 в escaped TSV. Каждая строка содержит
заголовок, URL и текст статьи. Экспортёр читает записи MongoDB в порядке
`_id`, использует URL из записи, если он задан, и при необходимости ищет его
в PostgreSQL по идентификатору среди неудалённых страниц. Записи без заголовка,
текста или доступного URL пропускаются. Экспорт читает два хранилища без общей
транзакции, поэтому параллельное обновление данных может влиять на выгрузку.
[Экспортёр](../tools/export_corpus.py).

После декодирования TSV заголовок и статья по отдельности превращаются в
массивы нормализованных строк. Индексатор присваивает документу последовательный
`DocId`, начиная с нуля, и превращает токены в плоский массив пар
`(терм, DocId)`. Токены учитываются в статистике до удаления повторов.
В прямой индекс записывается пара `{title, url}` на позиции `DocId`.
[Токенизатор](tokenizer.md) · [Реализация индексатора](../index/src/indexer.cpp).

TSV читает класс `CorpusReader`, общий для индексатора и замера токенизации.
Он восстанавливает экранированные поля, обрабатывает BOM, CRLF и пустые строки
и сообщает номер строки при ошибке. [Чтение корпуса](../index/src/corpus_reader.cpp).

## Сортировка и сборка обратного индекса

Внутри документа пары сортируются, после чего одинаковые термы сворачиваются
в одну пару с данным `DocId`. Глобальный массив содержит только уникальные
пары, отсортированные сначала по терму, затем по `DocId`. Один последовательный
проход формирует словарь и строго возрастающий список документов для каждого
терма. Булевому поиску достаточно присутствия терма в документе.

Оба этапа используют собственную итеративную сортировку слиянием.
Она даёт гарантированные `O(K log K)` сравнений для массива из `K` пар,
последовательно обходит массивы и подходит для перехода к внешнему слиянию.
Сравнение строк зависит от длины их общего префикса. Цена метода — второй
массив для слияния и перемещения строк. Один терм из разных документов
занимает несколько записей до построения словаря.

Пусть `N` — общее число токенов, `nᵢ` — число токенов документа, а `P` — число
уникальных пар `(терм, DocId)`. Сортировка требует
`O(Σ nᵢ log nᵢ + P log P)` сравнений. Удаление повторов внутри документов
уменьшает глобальный массив с `N` до `P`. К этой оценке добавляются чтение,
токенизация и линейная сборка списков.

## Двоичный формат

BIDX состоит из 64-байтового заголовка, каталога секций, прямого индекса,
словаря, списков `DocId` и статистики корпуса. Числа хранятся в little-endian
в полях фиксированной ширины. Строки UTF-8 имеют двоичные длины. Поля записей
читаются и записываются через их `operator>>` и `operator<<`.
Начиная с версии 1.1 отдельная секция сохраняет время построения и записи.
По этим двум значениям статистика API вычисляет общее время и скорость.

Версии major/minor, длина заголовка и типы секций позволяют добавить, например,
частоты или позиции. Читатель пропускает неизвестные необязательные секции.
Несовместимое изменение существующих полей требует новой major-версии.
Загрузчик проверяет размеры, смещения, порядок словаря и допустимость
`DocId`. Проверки целостности основаны на структуре файла.
[Побайтовая спецификация BIDX](../FORMAT.md).

## Ограничения и рост корпуса

Весь массив `P` пар и дополнительный буфер слияния находятся в оперативной
памяти. Основные кандидаты на сокращение затрат — повторяющиеся строки,
выделения памяти и сравнения строк при сортировке. Нынешние метрики разделяют
построение и запись, а длительность отдельных этапов внутри построения
в них не измеряется. Интернирование строк в собственном словаре или общий
буфер строк со смещениями могут уменьшить число выделений. При недостатке
памяти можно сортировать ограниченные серии пар, писать их на диск и сливать.
Delta-кодирование списков `DocId` и кодирование переменной длины уменьшают
объём файла.

При схожем составе корпуса память для пар растёт примерно линейно с `P`.
Если `P` увеличится в `k` раз, затраты глобальной сортировки по числу
сравнений вырастут примерно в `k × log₂(kP) / log₂(P)` раз. Сценарии ниже
предполагают пропорциональный рост числа документов и пар.

| Рост | Документы | Сравнения при глобальной сортировке | Ожидаемое ограничение |
|---|---:|---:|---|
| ×10 | 828 890 | ≈ ×11,4 | Около ×10 памяти для пар и буфера. При нехватке RAM нужны сортируемые блоки на диске. |
| ×100 | 8 288 900 | ≈ ×127,7 | Многопутевое внешнее слияние и сжатие индекса снижают потребность в RAM и дисковом вводе-выводе. |
| ×1000 | 82 889 000 | ≈ ×1 416,0 | Внешняя сортировка, параллельная обработка частей корпуса и разделение индекса снижают нагрузку на одну машину. |

Текущий предел формата составляет `2^32 − 1` документов. Смещения и счётчики
списков 64-битные. Все три сценария укладываются в предел `DocId`, но объём
промежуточных массивов ограничивает построение значительно раньше.
