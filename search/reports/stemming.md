# Поиск без учёта словоформ: русский стемминг

## Метод и включение в поиск

В отдельном модуле `morphology` реализован класс `RussianStemmer` по
[спецификации Snowball Russian](https://snowballstem.org/algorithms/russian/stemmer.html).
Это собственная реализация правил на C++, без готового стеммера и словаря.
Низкоуровневое чтение UTF-8 использует уже имеющийся utf8proc. Сначала
токенизатор выделяет слова и понижает регистр. Для полностью русских токенов
стеммер заменяет `ё → е`, определяет области RV, R1, R2 и последовательно
обрабатывает окончания деепричастий, возвратные, прилагательные, причастия,
глагольные и именные окончания, затем суффиксы и завершающие буквы.
В каждой группе выбирается самое длинное допустимое окончание.

Латинские, числовые и смешанные токены сохраняются. Стем — техническая основа,
например `машина`, `машины`, `машиной → машин`; словарные леммы не вычисляются.
Алгоритм не определяет значение слова и часть речи по контексту. Нерегулярные
пары могут оставаться разными: `павел → павел`, `павла → павл`.
Объединение форм также может быть избыточным: `сталь`, `стал`, `стали → стал`.

Исходный прямой и обратный индексы сохраняются. При создании поискового
движка один раз строится второй отсортированный словарь основ. Списки исходных
форм объединяются собственным сбалансированным слиянием без повторов DocId.
Готовый снимок сервиса содержит оба представления и публикуется после
построения. Читатель удерживает свой снимок при параллельной загрузке другого.
Время загрузки включает чтение, SHA-256, подготовку основ и частотного анализа.
[StemIndex](../boolean_search/src/stem_index.cpp) · [Срок жизни снимков](../service/src/index_store.cpp).

В полном корпусе **512 740 словоформ** образовали **199 448 ключей поиска**.
Число документов и исходных токенов не изменилось. Частоты для графика Ципфа
продолжают относиться к исходным словоформам.

По умолчанию выбран `mode=stem`. В режиме `exact` действуют прежние правила
нижнего регистра, включая различение `ё/е`. Парсер сначала распознаёт булевы
операции, затем ищет каждый операнд в выбранном представлении. Поэтому
`!слово` в режиме stem исключает всю найденную группу форм. Результаты идут
по DocId; в веб-выдаче по-прежнему 50 документов на страницу.

```sh
search/build-clion-userver/boolean_search search/data/corpus.bin --mode stem \
  < search/data/relevance-queries.txt > search/build-clion-userver/forms.jsonl
search/build-clion-userver/boolean_search search/data/corpus.bin --mode exact \
  < search/data/relevance-queries.txt > search/build-clion-userver/exact.jsonl
```

В веб-форме режим задаётся флажком «Искать все словоформы», сохраняется в URL,
ссылках пагинации и истории. API поиска и замеров принимает `mode=stem|exact`.
CLI сохраняет прежние поля и коды завершения, добавляя `mode` в записи.

## Набор оценки качества

Использован диагностический набор **16 запросов**: 10 обычных сочетаний
словоформ, 4 случая неоднозначности и 2 запроса с отрицанием. Формулировки
намерений сохранены до разметки в [relevance-queries.json](../data/relevance-queries.json).
Для каждого запроса собран пул — объединение первых 20 результатов каждого
режима. Получено **486 оценок**, относящихся к **444 различным документам**.

Оценки подготовлены ассистентом по заголовкам, началам текстов и целевым
фрагментам исходных статей. Это диагностическая разметка, а не независимая
человеческая эталонная коллекция. Релевантным считался документ с содержательным
фрагментом по сохранённому намерению. Случайное упоминание, биографическая
справка или ссылка «Читайте также» сами по себе не считались релевантными.
Каждое решение сохраняет DocId, URL, заголовок и пояснение.
[Все оценки](../data/relevance-judgments.json).

Набор привязан к SHA-256 конкретного BIDX:
`cbd151d60081b2185cd9c70aac5ddbf5d004d57391862c6dd3efffbd124f733b`.
Сервис проверяет совпадение файла, идентичность документов, уникальность оценок
и наличие разметки для всех результатов top-20. Неразмеченный результат не
приравнивается к нерелевантному: замер завершается ошибкой. Загрузка другого
корпуса делает этот набор недоступным.

Определения метрик:

- `P@20 = число релевантных в первых 20 / 20`. Недостающие позиции при короткой
  выдаче дают нулевой вклад; знаменатель всегда 20.
- `R_pool@20 = число релевантных в первых 20 / число релевантных во всём пуле`.
  Это полнота только относительно размеченного пула, а не всего корпуса.
  Для нулевого числа релевантных в пуле используется 0.
- Итоговые средние — макросредние по всем 16 запросам. На каждый режим
  выполняется один прогрев и три измеряемых поиска. Таймер исключает загрузку,
  подготовку словаря, разметку, сериализацию и HTTP.

Для `сталь` число совпадений выросло с 72 до 20 062, но P@20 упало
с 0,65 до 0. Причина — объединение существительного с частыми глагольными
формами; ранние по DocId нерелевантные документы вытеснили новости о материале.
Это ошибка избыточного объединения, которую суффиксные правила не различают.

Для `орган` P@20 снизилось с 0,05 до 0. Слово многозначно уже в точной форме:
намерение связано с музыкальным инструментом, а расширение добавляет
«органы» власти и анатомические органы. Концертный фрагмент исчезает из top-20.
Для `Лена` P@20 снизилось с 0,15 до 0,05: основа объединяет формы имени,
название реки и другие написания. Нижний регистр уже убрал сигнал собственного имени.

Для `осёл` точная выдача пуста, после `ё → е` и удаления окончаний найдено
59 документов. В размеченных первых 20 нет материала о биологии/использовании
животного: встречаются «осел», «осели», художественные и метафорические
употребления. Нулевой R_pool не доказывает отсутствия подходящих статей во
всём корпусе: документы за пределами пула не оценивались.

Отрицание также требует осторожности. В `университет !студенты` расширяется
и положительный, и отрицательный операнд. Новость об управлении вузом может
потеряться, если лишь попутно упоминает «студентом». Поэтому точная выдача не
обязана быть подмножеством новой выдачи для запросов с `!`.

## Возможные улучшения

Существующий переключатель точной формы позволяет вернуть прежний результат
для неоднозначного запроса, сохраняя поведение остальных запросов. Возможное
дальнейшее расширение — точность для отдельного помеченного операнда:
например, фиксировать `сталь`, продолжая расширять остальные слова запроса.
Такого синтаксиса в текущем парсере нет.

Для положительных запросов можно сначала выдавать точные совпадения в прежнем
порядке, затем остальные результаты расширения. Поскольку положительное
расширение сохраняет исходные совпадения, это сохранит прежний P@20 при
полной точной первой странице и позволит дополнить короткую страницу.
Текущая реализация сохраняет общий порядок DocId. Для отрицаний такая гарантия
не действует: сначала нужно определить требуемую семантику исключения.

Контекстная морфология, сохранение информации об именах и части речи,
разделение омонимов и ограничение `ё/е` контекстом могут уменьшить смешение
значений. Их нужно проверять на отдельном наборе с независимой разметкой:
подгонка исключений под эти 16 запросов не даёт гарантии для других запросов.
Иррегулярные формы потребуют словаря или дополнительных правил.
