# ЛР4 — Булев поиск

## Разбор и вычисление запроса

```text
expression  := conjunction { "||" conjunction }
conjunction := unary { ("&&" | неявное И) unary }
unary       := { "!" } (term | "(" expression ")")
```

Приоритет от высшего к низшему — НЕ, И, ИЛИ. Соседние операнды означают И.
Например, `руки !ноги` равнозначно `руки && !ноги`. Парсер использует рекурсивный
спуск и вычисляет выражение в процессе разбора. Повторные знаки `!` сводятся
к чётности. Перед поиском термов применяется тот же токенизатор, что и при
индексации. Пределы запроса — 65 536 байт UTF-8, 4 096 лексем и 128 уровней скобок.
[Парсер](../boolean_search/src/query_parser.cpp) · [Правила токенизации](tokenizer.md).

Терм ищется двоичным поиском по словарю за `O(log V)` сравнений, где `V` —
число термов. Пересечение и объединение проходят двумя указателями по спискам
длин `a` и `b` за `O(a+b)`. НЕ строит дополнение относительно всех `D` документов
за `O(D)`. Неизвестный терм даёт пустой список, его отрицание — все документы.
Пустой запрос даёт пустую выдачу. Результаты упорядочены по `DocId`.
[Списковые операции](../boolean_search/src/query.cpp).

## Сервис

Сервис userver загружает BIDX при запуске. `GET /api/search` возвращает общее
число совпадений и до 50 пар «заголовок, ссылка» из прямого индекса. Страницы
нумеруются с 1. При ошибке синтаксиса API возвращает HTTP 400, а введённый запрос
остаётся в форме. На `/` доступны форма, выдача, переход к следующей странице,
статистика из `GET /api/stats` и запуск замеров через `POST /api/benchmark`.
Заголовки выводятся как текст, ссылки допускают схемы HTTP и HTTPS.
Переходы «Назад» и «Далее» — ссылки с адресами `/?q=…&page=…`.
Обычный переход обновляет выдачу на странице, открытие в новой вкладке
использует тот же адрес. На границе отсутствующее направление недоступно.
[API и запуск](../README.md).

## Скорость выполнения запросов

14 ноября 2026 года нативная сборка CLion `macos-userver`
(`RelWithDebInfo`, macOS ARM64) выполнила замер на сохранённом индексе
82 889 документов. Сервис обработал 10 запросов, по 100 измеряемых
повторений после одного прогрева. Загрузка индекса заняла **374,222250 мс**,
среднее вычисление запроса — **0,251260 мс**.

| `(красный \|\| желтый) автомобиль` | 29 | 0,002833 | 0,003062 | 0,012125 |
| `руки !ноги` | 1 588 | 0,111417 | 0,119262 | 0,139000 |

| `и \|\| в \|\| на \|\| не \|\| что \|\| это` | 82 877 | 0,815750 | 0,890552 | 1,020708 |
| `!(россия \|\| москва) && (и \|\| в)` | 59 578 | 0,427875 | 0,489851 | 0,620042 |

Для повторения запустите сервис с `SEARCH_INDEX=data/corpus.bin` и отправьте
`{"repetitions":100}` на `POST /api/benchmark` или запустите те же запросы на
вкладке «Замеры». Число совпадений по всем десяти запросам совпало с замером
от 6 ноября 2026 года. Старый запуск до перехода на userver дал в среднем
0,246194 мс на запрос. Каждый набор времени получен за один запуск.
[Запросы](../data/benchmark-queries.txt) · [Замер userver](../data/userver-query-metrics.json) · [Ранний замер](../data/query-metrics.json).

Таймер внутри сервиса охватывает разбор запроса, поиск термов и операции
со списками. Загрузка индекса измеряется отдельно. Сериализация выдачи и
передача по HTTP происходят за пределами измеряемого участка.

Медленные запросы создают большие промежуточные списки. Цепочка
`и || в || на || не || что || это` несколько раз объединяет длинные списки
частых слов. В `!(и && в) || !(на && не)` строятся два дополнения относительно
всего корпуса. Даже запрос с небольшим результатом, например
`(россия || москва) && (политика || экономика) !спорт`, вычисляет дополнение
для `спорт` по всем документам.

Для `k` операций над плотными списками время и суммарный объём временных
выделений могут достигать `O(kD)`. Номер страницы задаёт срез готового списка,
поэтому отображение 50 результатов не сокращает объём поиска. Прямая разность
для `A !B`, обработка коротких списков при пересечениях первой и отложенные
дополнения могут уменьшить объём вычислений. При увеличении корпуса в 10, 100
или 1000 раз проход по плотному списку вырастет примерно во столько же,
если доля документов с термом сохранится.

## Проверка корректности

GoogleTest проверяет приоритеты и скобки, неявное и явное И, повторное НЕ,
неизвестные термы, пустые запросы, ошибки операторов и предел вложенности.
Для 500 детерминированно сгенерированных выражений ожидаемый ответ вычисляется
отдельно для каждого документа по булевым значениям принадлежности термов.
В эталоне не используются списковые операции поискового движка.
[Тесты булевой семантики](../tests/test_search.cpp).

HTTP-тесты запускают индексатор и сервис с корпусом из 56 документов.
Они проверяют выдачу из 50 и 5 результатов для запроса с 55 совпадениями,
заголовки и ссылки, регистр, параллельные запросы, ошибки синтаксиса и номера
страницы. Тесты замеров дополнительно проверяют число запусков и совпадений,
диапазон времени и обработку неверного JSON.
[Интеграционные тесты](../tests/test_web_api.cpp).

19 ноября 2026 года пройдены **все 56** тестов. Измерения производительности
выполняются через приложение, для unit-тестов используются проверки результатов
и формул. [Полный журнал](test-results/gtest.txt).

Утилита `boolean_search INDEX.bin` читает запросы из stdin и пишет JSON Lines
в stdout. Отдельная строка содержит запрос, число совпадений, время и весь список
документов. Ошибки запросов дают записи `error` и код завершения 2, операционные
ошибки дают код 1 и сообщение в stderr.

Из корня репозитория можно повторить запуск тестов и создание дампа.

```sh
ctest --test-dir search/build-clion-userver --output-on-failure --parallel 6
search/build-clion-userver/boolean_search search/data/corpus.bin \
  < search/data/queries.txt > search/build-clion-userver/results.jsonl
```

К отчёту приложены [запросы](../data/queries.txt),
[дамп демонстрационного индекса](test-results/search-demo.jsonl) и
[полный дамп корпуса в gzip](test-results/search-corpus.jsonl.gz).
В шести запросах к корпусу получено соответственно **11, 29, 1 588, 3, 81 044
и 17 600** совпадений. Порядок — возрастающий DocId.
[Проверка API на корпусе](test-results/upload-corpus.json) также сравнила выдачу
с CLI и повторила 1 000 измеряемых поисковых запусков с прежними числами совпадений.

Дополнительно JavaScript страницы выполнен в Node с имитацией DOM и управляемыми
ответами запросов. Проверены замена статистики без дублирования строк, очистка
результатов и пагинации, игнорирование старых ответов и сохранение выдачи при
ошибке загрузки. Также проверены адреса пагинации, открытие ссылки с Ctrl
и выбор замера токенизации с отдельными настройками и таблицей.
[Журнал проверки логики страницы](test-results/frontend.txt).

Загрузка через интерфейс активирует индекс для текущего запуска сервиса.
При перезапуске снова загружается настроенный файл. Снимок данных закрепляется
на всё время поискового запроса или замера, поэтому параллельная загрузка
не меняет документы и списки внутри выполняемого запроса.
